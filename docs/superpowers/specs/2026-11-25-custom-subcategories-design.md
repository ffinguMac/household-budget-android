# 내 세부 카테고리(직접 추가) 설계

작성일 2026-11-25 · 기준 브랜치 `master` (4f2e771)

## 의도
예전의 자유 카테고리 관리(대분류·소분류 추가/이름 변경/삭제/순서 변경)는 **관리 자체가 일**이라 없앴고, 고정 트리(`FixedCategories.TREE`)로 바꿨다. 그런데 고정 세부 항목만으로는 "반려동물", "헬스장"처럼 자기 생활에만 있는 항목을 따로 볼 수 없다. 관리 화면을 되살리지 않고, **거래를 넣는 그 자리에서** 세부 항목 하나를 더하는 것만 허용한다. 손이 안 가면 알아서 눈앞에서 사라지게 해 정리 부담도 없앤다.

## 목표 / 비목표 / 하지 않을 것
- 목표: 고정 대분류(지출·수입·저축) 아래에 사용자가 세부 항목을 직접 추가·이름 변경·삭제. 단, 고정 세부가 하나뿐인 대분류(지금은 유동 지출)는 제외. 통계·예산·자동 기록은 손대지 않아도 그대로 동작.
- 비목표: 고정 세부 항목의 수정, 세부 항목 순서 변경, 검색 시트에서의 추가, 유동 지출 아래 추가.
- 하지 않을 것(되돌아가면 실패): 대분류 만들기, 순서 변경, 색·이모지 고르기, 카테고리 관리/설정 화면.
- 실패 조건: 삭제·시드·마이그레이션으로 거래나 학습 규칙이 사라짐. 고정 항목이 편집됨. 직접 추가한 항목 때문에 예산·통계 합계가 어긋남.

## 검토한 안 (사용자 선택: A)
| 안 | 내용 | 결정 |
|---|---|---|
| A 고정 대분류 + 내 세부 항목 | 대분류는 고정, 세부만 선택 화면에서 추가 | **채택** |
| B 태그 | 카테고리는 그대로 두고 거래에 자유 태그 | 기각 — 통계·예산·자동 분류가 전부 카테고리 기준이라 태그용 축을 새로 만들어야 함 |
| C 완전 자유 편집 | 예전 관리 화면 복원 | 기각 — 없앤 이유(관리 부담)가 그대로 돌아옴 |

## 지금 코드에서 확인한 사실
- **고정/직접 추가 구분용 컬럼은 없다.** `categories`에는 `name, kind, parent_id, sort_order, icon`뿐. → 구분은 **이름으로 파생**한다: 세부 항목의 (종류, 대분류 이름, 이름)이 `FixedCategories.TREE`에 있으면 고정, 없으면 직접 추가. 직접 추가 이름은 고정 이름과 같을 수 없게 막으므로 파생이 항상 맞다.
- **시작 시 "보충/정리" 로직은 없다.** `AppDatabase.seedCategoriesIfEmpty`는 `count() > 0`이면 아무것도 하지 않고, `MIGRATION_6_7`은 v6 DB에서 한 번만 돈다(직접 추가가 생기기 전). 즉 지금은 모르는 세부 항목을 지우거나 바꾸는 코드가 없어 **고칠 것은 없고**, 회귀 테스트로 고정해 둔다. 앞으로 보충 로직을 만들면 "고정 대분류 아래의 고정 아닌 세부 항목은 사용자 것 — 지우지도 바꾸지도 않는다"가 규칙이다.
- **예산은 대분류 id에 건다.** `category_budgets.category_id`는 대분류를 가리키고(`BudgetSettingsScreen`), 쓴 돈은 `parentCategoryId`로 묶는다. 통계도 `row.parentCategoryId ?: row.categoryId`. → 직접 추가 항목의 거래는 **자동으로 대분류 예산·통계에 합산**된다. 세부 항목별 예산은 없다(지금도 없음).
- `transactions.category_id`는 `RESTRICT` FK → 거래를 먼저 옮겨야 지울 수 있다. `merchant_rules.category_id`는 FK가 없고, 없는 id를 가리키면 `AutoEntryRepository`가 그 규칙을 조용히 무시한다 → 삭제 때 같이 옮겨야 학습이 유지된다.
- `auto_entries`에는 카테고리 컬럼이 없다 → 확인 대기 항목은 삭제의 영향을 받지 않는다.
- 색·이모지는 `categoryStyleOf(대분류 이름)` → 직접 추가 항목은 설정 없이 대분류 것을 물려받는다.
- Room 버전 8. **이번 변경은 스키마를 건드리지 않는다**(아래 "자동 숨김").

## 결정

### 1. 만들기
- 선택기(`CategoryPicker`)에서 대분류를 펼치면 세부 칩 끝에 **"+ 직접 추가"** 칩. 누르면 이름 입력 대화상자 → 저장하면 만들어지고 **바로 그 항목이 선택**된다(거래 입력에서는 선택, 확인 필요 화면에서는 그 항목으로 정리).
- **고정 세부가 하나뿐인 대분류(지금은 유동 지출)에는 직접 추가할 수 없다.** 누르면 지금처럼 "기본"이 바로 선택되고 펼쳐지지 않는다. 화면에 추가 칩이 나오지 않고, 저장소도 이런 대분류에 대한 추가를 거부한다. 대분류 타일에 길게 누르기 동작은 없다.
- 저장값: `kind` = 대분류의 종류, `icon` = null, `sort_order` = 형제 최댓값 + 1(항상 고정 항목 뒤, 만든 순서).

### 2. 이름 규칙 (만들기·이름 바꾸기 공통)
- 앞뒤 공백 제거 후 1–10자(코드포인트 기준).
- 같은 대분류 안에서 겹치지 않음. 비교는 **대소문자·공백 무시**("카 페" = "카페", "Gym" = "gym"). 그 대분류의 고정 세부 이름과도 같을 수 없음.
- 다른 대분류에 같은 이름이 있는 것은 허용.

### 3. 이름 바꾸기 / 삭제
- 직접 추가한 칩(선택기)·행(더 보기 시트)을 **길게 누르면** 이름 입력 대화상자가 이름이 채워진 채 열리고, 그 안에 "삭제" 버튼이 있다. 고정 항목은 길게 눌러도 반응 없음.
- 이름 바꾸기는 `categories.name`만 바꾼다. 거래·규칙은 id로 묶여 있어 그대로 따라온다.
- **삭제 시 옮길 곳은 사용자가 고른다.** 삭제 확인 대화상자에 같은 대분류의 **고정 세부**가 칩으로 나오고, 기본값이 미리 선택되어 있다. 기본값 규칙: "기타"가 있으면 "기타", 없으면 "기본", 없으면 첫 번째 고정 세부.

  | 대분류 | 기본값 | 대분류 | 기본값 |
  |---|---|---|---|
  | 식비 | 식사 | 여가 | 문화 |
  | 교통 | 대중교통 | 기타 | 기타 |
  | 생활 | 통신 | 수입 | 기타 |
  | 쇼핑 | 의류/미용 | 저축 | 기타 |

- 확인 문구: 거래가 있으면 "거래 N건은 '<고른 곳>'(으)로 옮겨요."(칩을 바꾸면 문구도 바뀜) + 칩. 거래가 없으면 "거래가 없어서 바로 지워요."만 보이고 칩은 없다(학습 규칙은 기본값으로 옮김).
- 다른 직접 추가 항목은 옮길 곳이 될 수 없다(고정 세부만).
- 한 Room 트랜잭션에서: ① 거래 `category_id` 옮기기 ② `merchant_rules.category_id` 옮기기 ③ 카테고리 행 삭제. 저장소는 고른 id를 받아 **같은 대분류의 고정 세부인지 확인**하고, 아니면 **아무것도 하지 않는다**. 고정 항목·대분류 id를 지우려는 호출도 거부.
- 거래 메모에는 옛 이름을 남기지 않는다(대분류가 같아 합계는 그대로고, 사용자가 옮길 곳을 직접 고른 것이므로).
- 거래 입력 중에 지금 선택된 항목을 지우면 선택을 옮길 곳으로 바꾼다(저장 시 "없는 카테고리" 오류 방지).

### 4. 자동 숨김 (스키마 변경 없음)
- "마지막 사용일" = 그 항목 거래의 `MAX(occurred_epoch_day)`. 쿼리 하나(`GROUP BY category_id`, 기존 인덱스 사용)로 얻는다.
- 숨김 조건: 직접 추가 항목이고, 거래가 **하나 이상 있고**, 마지막 사용일이 오늘보다 90일 넘게 전.
- 숨겨진 항목은 선택기의 칩에서 빠지고, **"더 보기" 시트에는 항상 나온다.** 다시 쓰면(최근 날짜 거래가 생기면) 저절로 돌아온다. 지금 선택된 항목은 숨김 대상이어도 칩에 보인다.
- **한 번도 안 쓴 항목은 숨기지 않는다.** 만든 날짜를 저장하지 않아 "90일 동안 안 썼다"를 알 수 없기 때문. 거래가 없으니 길게 눌러 손실 없이 지울 수 있다. 이것까지 숨기려면 `categories.created_epoch_day` 컬럼 + v9 마이그레이션이 필요한데, 실제 데이터가 든 DB의 마이그레이션 위험에 비해 얻는 것이 작아 하지 않는다.
- 고정 항목은 절대 숨기지 않는다.

### 5. 자동 기록
- 학습 규칙은 카테고리 id를 저장하므로 직접 추가 항목을 그대로 가리킬 수 있다(코드 변경 없음). `AutoClassifier`의 기본 분류는 고정 경로만 쓴다.
- `findLeafByPath`(이름으로 고정 세부 찾기)는 직접 추가 이름이 고정 이름과 겹칠 수 없으므로 영향 없음.

### 6. 화면 규칙
- 문구는 해요체, `res/values/strings_components.xml`. 색은 `colorScheme`만, 글자 여섯 슬롯, `Space`·`shapes` 토큰, 터치 대상 48dp 이상(`docs/superpowers/plans/2026-11-22-ui-redesign.md` Global Constraints).
- 길게 누르기에는 접근성 라벨("이름 바꾸기·삭제")을 붙여 TalkBack에서도 쓸 수 있게 한다.
- 직접 추가 칩은 고정 칩과 똑같이 생겼다(구분 표시 없음).

## 엣지 케이스
- 대분류의 직접 추가 항목이 모두 숨겨짐 → 그 대분류는 고정 항목만 있는 것처럼 동작(추가 칩은 그대로 나온다).
- 나중에 고정 트리가 바뀌어 직접 추가 항목이 있는 대분류의 고정 세부가 하나가 됨 → 기존 직접 추가 항목은 그대로 쓰고 편집·삭제할 수 있다. 새로 추가만 막힌다.
- 과거 날짜(90일보다 전)로만 쓴 새 항목 → 저장 직후 숨김 조건에 걸린다. 더 보기에서 고를 수 있고, 최근 날짜로 쓰면 돌아온다. 받아들인다.
- 나중에 고정 트리에 같은 이름의 세부가 추가됨 → 그 직접 추가 항목은 그때부터 고정으로 취급된다(편집 불가, 거래 유지). 데이터 손실 없음.
- 삭제된 항목 id가 "최근 카테고리" 설정에 남음 → 화면이 없는 id를 걸러 내므로 문제없음.
- 삭제와 알림 자동 기록이 동시에 일어남 → 규칙은 같은 트랜잭션에서 옮겨지므로 다음 기록부터 옮길 곳으로 간다. 그 찰나에 옛 id로 들어오는 기록은 FK 오류로 실패할 수 있다(코드 리뷰에서 `AutoEntryRepository`의 기존 실패 처리 확인).
- CSV 내보내기는 이름을 쓰므로 바뀐 이름·옮겨진 거래가 그대로 반영된다.
